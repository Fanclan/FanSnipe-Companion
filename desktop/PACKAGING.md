# Distribution development

The desktop shell runs the engine in an Electron utility process. Closing the window leaves the tray and engine running; Quit asks the engine to stop and finalize jobs. The tray includes pairing approval, folder selection, diagnostics, legacy import, and an opt-in login item. The engine, dashboard, tools, Deno JavaScript runtime, and their licenses are local resources. Set the exact production portal origin in desktop/config.json before building; no preview wildcard is accepted. Electron's utility process supplies Node 24 with `node:sqlite`; no native SQLite addon is built or shared with the container.

Build the portal dashboard first, then in the companion root run `npm ci && npm run build`. After the FanSnipe dashboard artifact is published and reviewed, regenerate the checked-in dashboard lock from that immutable artifact with `node scripts/packaging-dashboard-lock.mjs ../FanSnipe-Portal/dist-dashboard ../FanSnipe-Portal/artifacts/dashboard-v0.1.1.tar.gz`. Refresh it whenever the dashboard changes. Run `scripts/packaging-ffmpeg-build.sh darwin-arm64` to build FFmpeg from source before staging. Windows builds also need `dotnet publish src/windows/JobRunner.csproj -c Release -r win-x64 --self-contained true -o build/windows` and an MSYS2 UCRT64 compiler. Use `node scripts/packaging-inputs.mjs darwin-arm64 ../FanSnipe-Portal/dist-dashboard /tmp/fansnipe-input.json`, then `node scripts/packaging-stage.mjs /tmp/fansnipe-input.json`. Replace the target with darwin-x64, win32-x64, linux-arm64, or linux-x64. The stage script downloads pinned tools at build time, verifies all hashes and requires the dashboard to match every pinned file; it bundles the tool licenses and attribution. Run `cd desktop && npm ci && npm run pack -- --mac --arm64` on a Mac. Resulting candidates are unsigned beta artifacts, not notarized releases. For Linux, stage the dashboard and run `docker build -t fansnipe:local .`; the image builds FFmpeg for its target architecture.

Set `FANSNIPE_VERSION` to a verified published tag when using Compose; it intentionally has no default. The image defaults to a loopback-only host port in compose and allows 180 seconds for graceful stop. It runs as a non-root user and persists engine data and recordings in separate volumes. Docker pairing uses the locally generated setup token in `/data/setup-token` (mode 0600): access it through your local container administration and enter it only into the same-origin dashboard. To opt into LAN access set `FANSNIPE_BIND` to a specific LAN interface; anyone able to connect can reach the pairing screen, so protect access to the setup token and trust the network. For an HTTPS reverse proxy, set `FANSNIPE_PUBLIC_ORIGIN=https://your-host.example` in Compose so the engine validates the exact public origin. The Docker dashboard is same-origin; do not configure hosted-portal cross-origin access. Keep setup-token access private. Changes to upload destinations require the same operator setup token in the Docker dashboard.

Tool lock: official yt-dlp 2026.10.26 and Deno 2.9.8 binaries with hashes in `scripts/packaging-tools.json`. FFmpeg 9.0.2 is built from its source tarball, verified against the FFmpeg project signing key and pinned SHA-256, without GPL, nonfree or version-3 components. Builds fail unless both tools report LGPL and HTTPS support. The source archive, LGPL text and build script accompany each candidate; check the distribution obligations for each release. Source: https://ffmpeg.org/releases/ffmpeg-9.0.2.tar.xz. yt-dlp source and license are at https://github.com/yt-dlp/yt-dlp/tree/2026.10.26; Deno source and license are at https://github.com/denoland/deno/tree/v2.9.8.

The tag workflow builds unsigned beta candidates and requires protected production environment credentials for stable macOS signing/notarization and Windows signing. It requires the dashboard URL configured as a repository variable and checks the archive and every file against the committed dashboard lock. After desktop candidates it pushes a multiarch GHCR image with SBOM and provenance, then creates candidate checksums and a download manifest with GitHub attestations. These workflow paths have not yet been exercised end to end; do not advertise or publish until artifacts, signing, image and manifest are independently verified. GitHub Release publication remains a separate owner-controlled step.

Existing StreamSnipe desktop data is reused in place if its catalog exists and no FanSnipe catalog exists. The prior packaged application directory `streamsnipe-desktop` is checked first, followed by the alternative `StreamSnipe` directory. Existing recording settings remain in that catalog. New desktop installations default to a FanSnipe data directory and a FanSnipe recordings folder. If both catalogs exist, FanSnipe uses its own catalog and leaves the legacy catalog untouched.

For a Compose upgrade, stop active recordings, then stop the old service with its original Compose file and project name: `docker compose -p OLD_PROJECT -f /path/to/old/compose.yaml stop --timeout 180 streamsnipe`. Do not remove the volumes. Start the FanSnipe service with the same project name. The renamed service does not automatically stop the old container, which otherwise occupies the port and catalog lease. Compose preserves the legacy `streamsnipe-data` and `streamsnipe-media` volume keys so an existing installation using the same Compose project name keeps its data. If the directory or project name changes, set `COMPOSE_PROJECT_NAME` to the prior project name when starting FanSnipe; inspect existing volume names first. The old environment variables `STREAMSNIPE_VERSION`, `STREAMSNIPE_BIND`, and `STREAMSNIPE_PUBLIC_ORIGIN` remain fallback inputs; the new `FANSNIPE_*` values take precedence. Configure a verified image version explicitly; no `latest` fallback is assumed.

Windows eight-hour soak testing is deferred for beta at the user's direction. Windows candidate CI smoke tests are shorter and must not be described as an eight-hour pass.
